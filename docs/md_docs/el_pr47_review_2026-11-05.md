## The review, verbatim

> # Code review — FeatFloWer PR #47
>
> PR: EL volume-averaged stage: continuity constraint, coupling fixes, conservative form, CFDEM twins (https://github.com/rmuenste/FeatFloWer/pull/47)
>
> The PR introduces substantial changes to the Euler–Lagrange solver, including conservative volume-averaged continuity, pressure-projection correctors, pressure feedback, and particle-to-fluid coupling fixes.
>
> My review focuses on actual implementation risks rather than the reported validation results. The new implementation is reasonably well separated into modules, and the standalone flux-kernel tests are a useful addition. However, I found issues worth addressing before merging.
>
> ## Findings
>
> ### 1. Zero-element MPI workers can deadlock the continuity-source assembly
>
> P1 — High priority
>
> Location: el_volume_averaged.f90, EL_ADD_CONTINUITY_SOURCE (1842aed8, lines 288-313)
>
> The conservative form begins with a collective readiness check, explicitly designed to accommodate workers with no elements. However, immediately afterward, the function contains:
>
> ```
> nel = mesh%level(ilev)%nel
> IF (nel.LE.0) RETURN
> ```
>
> Later, other workers execute `MPI_Allreduce` calls over `MPI_COMM_SUBS`.
>
> If a worker has `nel = 0`, it returns without participating in those reductions. Other workers with elements block waiting for it.
>
> Suggested fix: Under the conservative form, do not return for `nel = 0`. Let that worker contribute zero-valued local arrays and participate in every collective. The source assembly already uses zero-initialized accumulators, making this approach natural.
>
> This is conditional on allowing empty-worker partitions. If the domain decomposition guarantees at least one element per worker, that invariant should instead be asserted explicitly.
>
> ### 2. Conservative flux code reads beyond the vertex-coordinate array
>
> P0 — Merge blocker
>
> Locations: el_transfer.f90 (layout check and transport-porosity reconstruction, lines 365-395); el_volume_averaged.f90 (flux evaluation, lines 542-558); el_va_flux.f90 (Q2 DOF gathering, lines 414-451)
>
> The new routines expect `coor(3,ndof)` containing coordinates for all Q2 degrees of freedom, but production passes:
>
> ```
> mesh%level(ilev)%dcorvg
> ```
>
> The existing mesh infrastructure allocates `dcorvg(3,nvt)` for vertex coordinates, not all Q2 degrees of freedom. The solver separately constructs full Q2 coordinates using `SetUp_myQ2Coor()`.
>
> The new layout checker immediately accesses coordinates using indices above `nvt`:
>
> ```
> coor(:,dofs(8+l))
> ```
>
> Those edge/face DOF indices lie outside the vertex array. Depending on compiler bounds checking, this is an out-of-bounds error or undefined behavior.
>
> Even if the layout check were bypassed, `EL_VA_CONSERVATIVE_READINESS` explicitly requires:
>
> ```
> SIZE(mesh%level(ilev)%dcorvg,2).GE.ndof
> ```
>
> which a normal vertex-only array cannot satisfy.
>
> Suggested fix: Build or obtain the actual Q2 coordinate array and pass it consistently to the layout check and flux evaluation. The new unit tests already use a separate `BUILD_DOF_COORDINATES` array, which explains why they would not catch this production integration error.
>
> I would verify this with a bounds-checked conservative-form run before relying on the reported conservation gates.
>
> Correction to finding 2: After tracing the mesh initialization more deeply, I found that this is not a confirmed defect. `refineMesh` aliases coarser levels' `dcorvg` pointers to the finest-level coordinate storage. The EL application also retains an additional refinement level, so the solver-level Q2 nodes are represented by vertices in that finer storage. The implementation's layout check is consistent with this convention.
>
> I withdraw the P0 finding above. The production coordinate mapping should still have an MPI integration test, but the array-size argument alone does not establish an error.
>
> ### 3. Advective continuity uses a porosity gradient inconsistent with relaxation and clipping
>
> P2 — Medium priority
>
> Locations: `el_transfer.f90`, `el_quadrature.f90`, `el_volume_averaged.f90`
>
> The new continuity source uses:
>
> ```
> adv = -DOT_PRODUCT(u, el_field_data%grad_alpha_p(:,iel))
> g = -(d_cont + adv)/eps
> ```
>
> This assumes grad eps_f = -grad alpha_p.
>
> However, the stored porosity is computed as eps_f^{n+1} = lambda eps_f^n + (1-lambda) max(1-alpha_p, eps_min), where lambda is `el_eps_f_relax`.
>
> Consequently:
>
> - With nonzero relaxation, the gradient must include the old porosity gradient and the relaxation factor.
> - When porosity is clipped at `el_eps_f_min`, the gradient of the clipped contribution is zero, but `grad_alpha_p` remains nonzero.
>
> The time derivative and advective gradient are therefore calculated from different effective fields.
>
> This does not affect the usual unclipped configuration with `el_eps_f_relax = 0`. But it can affect dense suspensions or runs using relaxation.
>
> Suggested fix: Either calculate a gradient consistent with the actual stored porosity or reject unsupported relaxation/clipping combinations in the advective form. The conservative formulation avoids this particular gradient approximation.
>
> ### 4. The bitwise comparison tool can report false success
>
> P2 — Medium priority
>
> Location: tools/el_stream_compare.py
>
> The comparison currently works on extracted floating-point tokens:
>
> ```
> for x, y in zip(ra, rb):    if x == y:        continue
> ```
>
> The `bitwise` status only checks the maximum numeric difference and line count. It does not require equal token counts or compare textual fields.
>
> This causes several problems:
>
> - A candidate missing trailing numeric fields can be reported as bitwise.
> - Changes to textual configuration or diagnostic labels are ignored.
> - Numerically equal values with different textual representations are treated as bitwise identical.
> - Most importantly, the script does not exit with a nonzero status when it reports `NOT BITWISE`.
>
> Given that this repository relies on stream comparison for certification, the checker deserves its own unit tests.
>
> Suggested fix: Distinguish exact textual/bitwise comparisons from comparisons of compatible numeric columns. Check token counts according to an explicit schema and return a nonzero exit status for failed comparisons.
>
> ### 5. Slurm submission scripts hide solver failures from the scheduler
>
> P2 — Medium priority
>
> Locations: el_slurm_submit_np.sh and fritz_el_submit_np.sh
>
> Both generated job scripts end with an `mpirun` invocation followed by:
>
> ```
> echo "exit=$?"
> ```
>
> Because `echo` normally succeeds, the batch script exits with status zero even when `mpirun` fails. Slurm can therefore report a completed job despite a simulation failure.
>
> The outer submission scripts use `set -eu`, but that does not carry into the generated batch scripts.
>
> Preserve and propagate the solver status instead:
>
> ```
> mpirun -np "$NP" "$BIN" > run_slurm.log 2>&1
> status=$?
> echo "exit=$status"
> exit "$status"
> ```
>
> ## What looks sound
>
> The following parts of the implementation appear consistent by static inspection:
>
> - Di Felice standard drag: the additional eps^2 factor changes the campaign form eps^(-chi) into eps^(2-chi), as intended.
> - Pressure feedback: the pre-advance feedback reconstruction now preserves the non-drag pressure reaction, addressing the described P5 issue.
> - Frozen-particle semi-implicit coupling: the `-B*u_f` adjustment has the intended algebraic sign for avoiding duplicate drag application.
> - BDF2 history: the separate rate-validity flags and previous-time-step handling are sensible, including the fallback to backward Euler.
> - Flux kernel: the face orientation, Q1-in-Q2 reconstruction, and row-residual implementation are coherent. The new tests cover several important geometric identities.
>
> These are positive assessments from reading the implementation, not independent numerical verification.
>
> ## Recommended actions before merging
>
> I would prioritize resolving the MPI participation issue in finding 1 and adding a small integration test covering the production conservative-form path on multiple ranks.
>
> The other changes are more localized. The gradient consistency issue should be addressed or constrained explicitly, and the validation utilities should be corrected so that certification failures cannot be mistaken for successes.
>
> Overall verdict: request changes before merging. The principal numerical design looks well developed, but the remaining MPI edge case and validation-tooling defects are worth fixing.
>
> Review scope: I examined the PR diff, principal Fortran modules, their integration into the existing Q2/P1 solver, relevant tests, and the new tooling. I did not compile the branch or execute the MPI validation campaigns. No files or GitHub review state were changed.
